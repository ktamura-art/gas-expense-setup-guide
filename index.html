フォルダとスプレッドシートを作る

先に置き場所を作ります。ここで控えた5つのIDを、あとでコードに貼り付けます。 メモ帳などを開いて、控えながら進めてください。

0-1共有ドライブに4つのフォルダを作る

既にある「領収書保管フォルダー」の隣に、下記3つを追加してください。

フォルダ名役割状態
領収書保管フォルダー領収書PDFを入れる場所（処理の入口）作成済み
02_処理済み正常に処理できたPDFの移動先。中に年月フォルダが自動でできます新規
03_エラー読み取れなかったPDFの移動先新規
04_検証用テスト用のPDFを置く場所（任意）任意

フォルダ名は上記のとおりでなくても構いません。あとでIDで指定するためです。

0-2フォルダIDを控える

フォルダを開いたときのURLの、/folders/ より後ろがIDです。

https://drive.google.com/drive/folders/1AbCdEfGhIjKlMnOpQrStUvWxYz01234 └──────── ここがID ────────┘

3つ（または4つ）ぶん、同じ要領で控えてください。上の例は「領収書保管フォルダー」の実際のIDです。

0-3ログ用のスプレッドシートを1つ作る

名前は「経費自動化_処理ログ」など分かるものにしてください。シートは空のままで構いません。必要なシートはコードが自動で作ります。

作られるシートは次の5つです。

シート名中身

締め処理レポート月3回の実行結果と、未提出の内訳
区間マスタだけ手で作ってください

1行目に見出し、2行目から中身を入れます。空でも動きますが、その場合は運賃が入りません。

A列      B列      C列        D列

URLの /d/ と /edit のあいだがIDです。

https://docs.google.com/spreadsheets/d/1ZyXwVuTsRqPoNmLkJiHgFeDcBa9876543/edit └──────────── ここがID ────────────┘

0-5カレンダーIDと通知先を決める

  • カレンダーID：実行する方ご自身のカレンダーを使うなら primary のままで構いません。他の方のカレンダーを見る場合は、そのカレンダーの設定画面の「カレンダーの統合」にあるカレンダーID（〜@group.calendar.google.com の形）を控えます。
  • 通知先メールアドレス：要確認・エラー・申請漏れの連絡先です。経理ご担当の方のアドレスを想定しています。
他の方のカレンダーを見る場合

そのカレンダーが、スクリプトを実行する方に共有されている必要があります。共有されていないと「カレンダーが見つかりません」で止まります。権限は閲覧のみで足ります。

STEP 1

Apps Scriptプロジェクトを作る

1-1新しいプロジェクトを作る

https://script.google.com/
script.google.com を開く→新しいプロジェクト

左上の「無題のプロジェクト」をクリックして、名前を 経費自動化 に変更してください。

議事録連携とは別プロジェクトにしてください

経費自動化と議事録連携の両方に now_() という同じ名前の関数があります。同じプロジェクトに入れると、あとから読み込まれたほうが優先され、意図しない動きになります。必ず別々のプロジェクトとして作ってください。

STEP 2

マニフェストを差し替える

PDFを読み取る処理で Drive API を使います。ここを飛ばすと必ずエラーで止まるため、 コードを貼る前に済ませてください。

2-1マニフェストを表示する設定にする

左の歯車アイコン→プロジェクトの設定→「appsscript.json マニフェスト ファイルをエディタで表示する」にチェック

エディタに戻ると、ファイル一覧に appsscript.json が現れます。

2-2中身をまるごと置き換える

appsscript.json を開き、全選択して削除してから下記を貼り付けます。

{ "timeZone": "Asia/Tokyo", "runtimeVersion": "V8", "exceptionLogging": "STACKDRIVER", "dependencies": { "enabledAdvancedServices": [ { "userSymbol": "Drive", "serviceId": "drive", "version": "v2" } ] } }

保存（Ctrl+S ／ Cmd+S）してください。

こうなればOK

左の「サービス」欄に Drive が追加されていれば成功です。表示されない場合は、いったんページを再読み込みしてください。

うまくいかないとき

マニフェストを触らず、左の「サービス」の＋ → Drive API → バージョン v2 → 追加でも同じ結果になります。やりやすいほうで構いません。ただしタイムゾーンは別途「プロジェクトの設定」で 日本標準時 にしてください。

初期状態の Code.gs は使いません。ファイル名の右の「⋮」から削除してください。

残しておくと myFunction が実行対象の一覧に出てきて紛らわしくなります。

3-25つのファイルを追加する

ファイルの右の ＋→スクリプト→名前を入力

ファイル名は下記のとおりにしてください（拡張子 .gs は自動で付きます）。順番はどれからでも構いません。

付ける名前貼り付ける元ファイル要否
メイン01_経費自動化_メイン.gs.txt必須
締め処理02_経費自動化_締め処理.gs.txt必須
表記ゆれ辞書03_経費自動化_表記ゆれ辞書.gs.txt推奨
区間料金と命名規則04_経費自動化_区間料金と命名規則.gs.txt任意

STEP 4

CONFIGを自社の環境に書き換える

書き換えるのは 「メイン」ファイルの先頭にある CONFIG だけです。他のファイルは触らなくて構いません。

4-16項目を埋める

「メイン」を開き、上から20行目あたりの const CONFIG = { の中を書き換えます。

項目入れるもの準備の番号
FOLDER_IN領収書保管フォルダーのID0-2
FOLDER_DONE02_処理済み のID0-2
FOLDER_ERROR03_エラー のID0-2

書き換え後はこのような形になります。

const CONFIG = {
  FOLDER_IN:    '1AbCdEfGhIjKlMnOpQrStUvWxYz01234',
  FOLDER_DONE:  '（02_処理済みのID）',
  FOLDER_ERROR: '（03_エラーのID）',

  LOG_SHEET_ID: '（スプレッドシートのID）',
  LOG_SHEET_NAME: '処理ログ',
  FARE_SHEET_NAME: '区間マスタ',

  CALENDAR_ID: 'primary',
  NOTIFY_EMAIL: 'keiri@example.co.jp',

  CLOSING_DAY: 20,
  ENABLE_MF: false,      ← ここは false のまま

ENABLE_MF は false のままにしてください

true にすると、テスト中の領収書がマネーフォワードへ登録されてしまいます。判定結果をひととおり確認したあと、STEP 9 で切り替えます。

よくある入力ミス
  1. IDをURLごと貼ってしまう（ID部分だけを貼ってください）
  2. 前後の シングルクォート ' を消してしまう
  3. 行末の カンマ , を消してしまう

いずれも赤い波線が出るので、保存前に確認してください。

STEP 6

領収書1件で本処理を試す

ここが山場です。いきなり全件入れず、1件だけで挙動を確かめてください。

6-1領収書PDFを1件だけ置く

FOLDER_IN に指定したフォルダに、PDFを1件だけ入れてください。

できれば、カレンダーに対応する予定がある日付の領収書を選んでください。突合まで通して確認できます。

6-2main を実行する

関数リスト→main→実行

ドライブ・スプレッドシート・カレンダー・メールの権限を求められます。STEP 5-3 と同じ手順で許可してください。

実行ログにこう出ればOK 
完了：正常 1 / 要確認 0 / エラー 0

「要確認 1」でも失敗ではありません。下記のどちらかを意味します。

  • その日のカレンダーに候補の予定が複数あった（どれか選べなかった）
  • その日に予定が無かった（摘要を手入力する必要がある）

いずれも処理ログの「備考」列に理由が入ります。

6-3結果を4か所で確認する

#見る場所確認すること
1処理ログ シート1行増えている。利用日が発行日ではなく搭乗日・乗車日になっている
2同上金額が合計額になっている（手数料の0円を拾っていない）
302_処理済み フォルダ年月フォルダ（例 2026-09）ができ、その中にPDFが移動している
4同上のファイル名20251127_JAL_34120_交通費.pdf の形にリネームされている
利用日がおかしいとき

領収書の書式が想定外の可能性があります。そのPDFをデジライズへ共有してください。判定ルールを追加します。実領収書4件では正しく取れていますが、書式は会社ごとに違います。

問題なければ、残りの領収書をまとめてフォルダに入れて main を再実行してください。

件数が多いとき

1回の実行は6分で強制終了されます。PDFのOCRは1件あたり数秒かかるため、目安として50〜80件を超えるときは分割してください。途中で止まっても、処理済みのファイルは移動しているので、そのまま再実行すれば続きから進みます。

STEP 7

カレンダー系の2つを動かす

実運用の準備として、カレンダー側の状態を可視化します。どちらも読み取りのみで、予定は変更しません。

7-1命名規則に合わない予定を洗い出す

関数リスト→scanCalendarNaming→実行

過去2ヶ月を走査し、prefix///詳細 の形になっていない予定を出現回数の多い順にシートへ書き出します。

「命名規則チェック」シートを開いてください

上位に来ているものが「毎月の定常訪問なのに規則外」の候補です。D列に、規則に合わせるか対象外にするかを記入していけば、そのまま運用ルールの整理表になります。

7-2辞書に無い地名を洗い出す

関数リスト→suggestDictEntries→実行

直近35日の move の予定から、辞書に登録されていない地名を抽出します。

「辞書の追記候補」シートを開いてください

出現回数の多い順に並んでいます。D列（正式表記）を上から埋めて、「表記辞書」シートへ移すだけで辞書が育ちます。全部埋める必要はありません。よく出るものから順にで構いません。

辞書を編集したあとは

1回の実行中は辞書を読み込み直しません（速度のためです）。編集した内容は、次回の実行から反映されます。
